# EventLens: быстрая проверка семантической гипотезы

Обновлено 2026-09-07 по требованию пользователя: минимум инженерии, максимум проверяемости. Этот документ заменяет прежний план M0–M6. Реализация эксперимента ещё не выполнена.

## Вопрос и границы

**Помогают ли новые события и их тип лучше прогнозировать будущий суточный риск BTC, чем рынок, количество сообщений и простой sentiment?**

Один актив, один горизонт, одна простая модель. Первый результат — честная exploratory-проверка на имеющейся истории. Старые периоды уже изучались: новый split не превращает их в независимое подтверждение.

Не нужны до первого результата: новый Python-пакет, Neo4j, GNN, облако, CI, система контрактов, registry, live-сервис и массовая переаннотация. Старые дефекты исправляем только там, где они влияют на этот эксперимент. [Аудит](PROJECT_AUDIT_2026-09-07_RU.md) остаётся справочником.

## 1. Подготовить один корректный набор данных

- Объединить BTC-часть и остальные TBSA-сообщения, проверить идентификаторы и дубликаты. Оригиналы сохранить; повторы можно учитывать отдельно от уникальных событий.
- Найти или восстановить полный ряд часовых цен. Если доступны только прореженные котировки, это конкретный блокер: интерполяция не восстанавливает реальные returns.
- Построить полную временную сетку; отличать отсутствие сообщений от неизвестного покрытия. Убрать views/forwards без исторического времени наблюдения.
- Цель: сумма квадратов часовых log returns будущих 24 часов. Чётко записать время решения и начало/конец цели; исторические returns в цель не входят.
- В небольшом разделе скрипта или README запуска записать допущение о доступности экспортных текстов и задержке обработки. Проверить, что используемая версия текста могла быть доступна. Не обещать live-достоверность без first_seen/истории правок.

**Готово, когда:** несколько конкретных временных примеров и проверки кода показывают правильные окна, нет скрытых разрывов рынка, таблица общая для всех сравниваемых вариантов.

## 2. Получить baseline до сложной семантики

Одна регуляризованная линейная модель с одинаковой процедурой обучения:

| Вариант | Входы |
|---|---|
| A | Прошлый риск за 1/7/30 дней, returns, volume |
| B | A + количество сообщений и источников, coverage |
| C | B + существующий target sentiment и простой словарный счётчик событий |
| D | C + семантические признаки из следующего шага |

Train-mean и persistence — дешёвые sanity checks, не отдельный исследовательский проект.

Даты выбрать по реальному покрытию до просмотра метрик. Сделать несколько последовательных train→test окон; исключить обучающие labels, ещё неизвестные на момент каждого fit. Scaler и небольшой подбор регуляризации обучаются только на train с временным внутренним разбиением. Все варианты оцениваются на одинаковых test dates.

Основная метрика: MSE прогноза будущего RV; сравнивать paired errors. Дополнительно — MAE и R². Это сознательное упрощение прежнего предложения QLIKE, сделанное до нового эксперимента. Не менять основной критерий после просмотра результата. Относительное снижение MSE считать против того же baseline на тех же датах.

## 3. Проверить две смысловые идеи

**Новизна:** новое событие, содержательное обновление и перепечатка — разные вещи. Сравнивать текст только с доступными прошлыми сообщениями, например за семь дней. Начать с простого поиска похожих текстов; фиксированные embeddings добавлять только если они действительно нужны для распознавания перефразов. Проверить ненулевое покрытие и совпадение message ID. Новизна относится к нашему корпусу, не ко всему интернету.

**Тип и статус:** различать взлом/остановку сервиса, регуляторное решение, прочие новости и комментарии о цене; сохранять отрицание, слух и сообщение о произошедшем событии. Начать с существующих аннотаций, нормализации категорий и небольших правил. Новые поля извлекать только если существующих недостаточно.

Проверить вручную примерно 100–150 сообщений и несколько десятков пар «повтор/обновление/новое событие», включая русский/английский, разные каналы и отрицания. Это sanity-check качества, не полноценный NLP benchmark. Если разметка ненадёжна, упростить категории или исправить extractor до проверки прогноза. Не выдавать ответы LLM за ручную разметку.

Добавить только несколько признаков: число новых событий, доля перепечаток, число новых событий выбранных типов, число слухов/опровержений при достаточной поддержке. Отдельно проверить C+новизна, C+тип/статус и их сочетание — без расширения поиска на десятки моделей.

Работы о [типах финансовых событий](https://aclanthology.org/D19-5105/) и [повторной информации](https://columbia.edu/~pt2238/papers/Tetlock_SSRN_Fit_to_Reprint.pdf) мотивируют эти гипотезы, но не гарантируют эффект для BTC.

## 4. Проверить, что прирост не является артефактом

- Посмотреть paired-разницу ошибок и её интервал с временным block bootstrap, параметры которого выбраны на train; сохранить результаты всех вариантов, а не только победителя. На изученной истории это оценка неопределённости exploratory-результата, не окончательное подтверждение после выбора лучшей гипотезы.
- Убедиться, что прирост есть сверх активности и простых словарных признаков.
- Отдельно посмотреть влияние крупнейших событий и доминирующего канала. Узкий эффект так и описать; не удалять неудобные периоды ради красивой метрики.
- Проверить исключение пересказов уже случившегося изменения цены и реалистичную задержку сообщений. При задержке цель остаётся строго будущей относительно решения.
- Если выигрыш есть только у дорогой новой разметки, добавить дешёвый TF-IDF baseline перед выводом о необходимости сложной семантики.

Современная языковая модель может знать исход старой новости. Извлечение по фрагментам текста и фиксация версии полезны, но не доказывают отсутствие такой памяти. Исторический результат с такой моделью остаётся ретроспективным; см. [Glasserman & Lin](https://arxiv.org/abs/2309.17322).

## 5. Закончить отчётом и принять решение

Достаточно одного скрипта, нескольких целевых тестов и одной папки запуска: параметры/окружение/хеши входов, predictions, метрики и короткий `RESULTS.md`. Не создавать отдельные реестры и отчёты ради управления этим объёмом работы.

В отчёте: сколько данных, какие даты/допущения, точная цель, таблица A–D, разброс эффекта, стоимость/время, что проверено и следующий шаг.

- **Прироста не видно:** зафиксировать результат в этой постановке. Широкий интервал означает неопределённость. Не запускать бесконечный перебор ради положительной цифры.
- **Есть устойчивый кандидат:** зафиксировать признаки и модель, затем проверить один раз на действительно неиспользованном периоде или новых данных. Отдельную инфраструктуру для этого строить заранее не нужно.
- **Семантика полезна только для группировки новостей:** это отдельный NLP-результат, не улучшение рыночного прогноза.

Ориентир — несколько рабочих дней до первой корректной таблицы, если есть полный рынок и доступна ручная проверка. Это оценка, не обещание срока независимого подтверждения. Первый рабочий пакет: проверить рынок, собрать общую таблицу и запустить A–C; затем добавлять смысловые признаки.
